# DANS v1.0.0

DANS puts a PostgreSQL-backed authorization and audit boundary in front of the PowerDNS Authoritative API. DNS queries continue to go directly to PowerDNS. This first release includes the API, CLI, and embedded browser console in one executable, with a generated Go client available from the Go module.

## Included workflows

- Manage zones and complete RRsets through the console, CLI, or API. Delegate RRset changes by exact or glob owner selector, record type, and change kind, with direct identity or group assignments.
- Manage identities, groups, memberships, API tokens, and zone bindings. Inspect retained assignments separately from current authority, and recover retired bindings without inheriting their old grants.
- Sign in to the console with an existing API token. Secure, HttpOnly, same-origin browser sessions retain current token and authority checks; signing out ends the browser session while preserving the original API token.
- Browse large zones through a rebuildable PostgreSQL index with pagination, owner-name search, record-type filtering, refresh status, and complete RRset editing.
- Inspect audit history and download filtered NDJSON. Interrupted exports fail the transfer so clients can reject incomplete downloads.
- Migrate, bootstrap, recover an existing operator token, and finalize a restore through offline commands in the same executable. Run coordinated same-version instances against one writable PostgreSQL primary.

## Artifacts and dependencies

The release provides checksummed static Linux amd64 and arm64 executables with embedded console assets, plus the multi-platform `ghcr.io/ncode/dans:v1.0.0` image. The container runs as UID/GID 65532 and contains the executable and CA roots; production does not require Node.js.

Verify `SHA256SUMS` and the executable's `version` output before giving it credentials. Use the versioned image tag for deployments. The [release guide](https://github.com/ncode/dans/blob/v1.0.0/docs/release.md) describes builds and verification.

DANS requires PostgreSQL 16–18 current minors on one writable primary and one PowerDNS Authoritative upstream in `>=5.1.3,<5.2`. Keep the PowerDNS management API private and place DANS behind trusted TLS ingress. The [deployment examples](https://github.com/ncode/dans/blob/v1.0.0/deploy/README.md), [database roles](https://github.com/ncode/dans/blob/v1.0.0/docs/operations/database-roles.md), and [initial migration and bootstrap runbook](https://github.com/ncode/dans/blob/v1.0.0/docs/operations/runbooks.md#initial-migration-and-bootstrap) describe installation.

## Operational boundaries

Authenticated DNS reads are shared. Delegated writes use allow-only policy; there is no per-identity read filtering, nested group membership, explicit deny rule, or per-record-value ownership. Unknown routes and unsupported upstream operations fail closed. See the [policy and v1 limitations](https://github.com/ncode/dans/blob/v1.0.0/docs/policy.md#explicit-v1-limitations).

Mixed-version rolling upgrades and in-place downgrades after migration are unsupported. Stop all instances before migration, then start only the matching target version. Backup and rollback require a verified pair of PostgreSQL and backend-specific PowerDNS copies. Follow the [upgrade guide](https://github.com/ncode/dans/blob/v1.0.0/docs/operations/coordinated-upgrades.md) and [restore runbook](https://github.com/ncode/dans/blob/v1.0.0/docs/operations/runbooks.md#restore-finalization).

Required CI exercises PostgreSQL 16 and 18, paired recovery and rollback, and the Docker Compose TLS deployment. Kubernetes examples are checked as configuration; cluster NetworkPolicy enforcement and Podman runtime behavior require deployment-specific verification.
